# Learning kube-rs

A step-by-step path from "connect to a cluster" to "a working operator running in
Kubernetes". Every step has a small exercise to build in this repo. The steps build on
each other, so do them in order.

Each step has the same parts:

- **Learn**: the concepts and APIs to read up on.
- **Build**: the exercise.
- **Done when**: how you know the step is finished.

The capstone project is a **`Webpage` operator**. You create a `Webpage` custom resource
containing some HTML, and the operator serves it with nginx: it creates a ConfigMap,
Deployment, and Service, keeps them in sync, and reports status back on the `Webpage`.

> **Versions.** This roadmap was last checked against **kube 5.0**, **k8s-openapi 0.29**
> (Kubernetes 1.37), and **schemars 1.x** in November 2026. kube ships a new major version
> for roughly every Kubernetes release, and small things move each time. If a name in this
> file doesn't exist, check [docs.rs/kube](https://docs.rs/kube) for the version in your
> `Cargo.lock` and the [changelog](https://github.com/kube-rs/kube/blob/main/CHANGELOG.md).
> Be wary of tutorials written for kube 0.x–2.x: they predate CEL validation in the derive
> macros, use `chrono` instead of `jiff`, and call APIs that have since been deprecated.

## Repo layout for the exercises

```text
src/
  lib.rs              # Webpage CRD types and shared code (examples import this)
  main.rs             # the operator
examples/
  02_connect.rs       # one file per step, prefixed with the step number
  03_list_pods.rs
  ...
  crdgen.rs           # prints the CRD manifest
tests/
  integration.rs      # cluster-dependent tests, marked #[ignore] (step 15)
manifests/
  crd.json            # generated by crdgen and committed (step 8)
  ...                 # RBAC and the operator Deployment (step 17)
```

Run an exercise with `cargo run --example 03_list_pods`. Examples can only import from the
library target, so the CRD types go in `src/lib.rs`. A package can have both `lib.rs` and
`main.rs`.

## Ground rules

These apply to every step. Each one is explained in the step where it first matters; they
are collected here so you can check your code against them as you go.

**Rust**

- **Typed errors in the library, `anyhow` at the edges.** `src/lib.rs` and the operator
  use a `thiserror` enum. Examples and `main` may return `anyhow::Result`.
- **No `unwrap()` on anything that comes from the cluster.** Nearly every field in a
  Kubernetes object is an `Option`. Use `?`, `as_deref()`, `unwrap_or_default()`, and
  edition-2024 let-chains (`if let Some(s) = &pod.status && let Some(p) = &s.phase`).
  A panic in a reconciler takes the whole controller down.
- **Fix lints, don't silence them.** CI runs `clippy::pedantic` with `-D warnings`. When a
  lint is truly wrong for one item, put `#[expect(clippy::..., reason = "...")]` on that
  item. Unlike `#[allow]`, `#[expect]` warns you when it is no longer needed.
- **Structured logs.** Use `tracing` with fields (`info!(name = %name, "reconciling")`)
  rather than `println!` or values baked into the message. Examples may `println!` their
  actual output.
- **Async hygiene.** A stream does nothing until it is polled. A future can be dropped at
  any `.await`, so every step of a reconcile has to be safe to repeat. Never block the
  runtime (`std::thread::sleep`), and don't hold a lock across an `.await`.
- **Share, don't copy.** `Client` and `Api` are cheap handles; clone them freely. Put
  shared state in one `Context` struct behind an `Arc`.
- **Declare only what you use.** Pick specific crate features instead of `full`.
- **Document public items.** Doc comments on CRD types become the field descriptions in
  `kubectl explain`.
- **Keep logic in pure functions** and test it next to the code. Leave I/O at the edges.

**Operators**

- **Level-triggered.** Reconcile from the current state of the world. Never depend on
  which event fired, or on having seen every event.
- **Idempotent.** Running reconcile twice in a row must change nothing the second time.
- **Server-side apply** is the default way to write, with one constant field manager
  name. Send only the fields you have an opinion about. (Step 13 has the one case in this
  roadmap where it is the wrong tool.)
- **Owner references** for children in the same namespace. Finalizers only for cleanup
  that garbage collection can't do.
- **`spec` belongs to the user, `status` to the controller.** The operator never edits the
  spec of its own resource.
- **Report through status.** `observedGeneration` plus conditions, with deterministic
  values so a status write doesn't trigger another reconcile.
- **Validate as early as possible.** Schema first, then CEL rules, and only then a
  condition set at reconcile time. Reach for an admission webhook last.
- **Least privilege.** The operator gets only the RBAC verbs it uses, and it does not
  install its own CRD.
- **Throwaway clusters only.** Everything here runs against a `kind-*` context.

## Phase 0: Foundations

### 0. Prerequisites

**Learn**

- Rust basics you will lean on constantly: ownership and `Arc`, traits and generics (`Api<K>` is generic over the
  resource type), `Option`/`Result` and `?`, and `serde`.
- Async Rust: `tokio`, `async`/`await`, and especially `futures::Stream` + `StreamExt`.
  The kube runtime is built on streams.
- Kubernetes objects: `apiVersion`/`kind`/`metadata`/`spec`/`status`, namespaces,
  labels and selectors, owner references, RBAC.
- The controller pattern: a reconcile loop that compares desired state to actual state
  and closes the gap.

**Read**

- [The Rust Book](https://doc.rust-lang.org/book/), in particular the chapters on error
  handling, traits, smart pointers, and async.
- [Tokio tutorial](https://tokio.rs/tokio/tutorial)
- [Kubernetes: Objects](https://kubernetes.io/docs/concepts/overview/working-with-objects/),
  [Controllers](https://kubernetes.io/docs/concepts/architecture/controller/),
  [Operator pattern](https://kubernetes.io/docs/concepts/extend-kubernetes/operator/)
- [kube.rs: controller introduction](https://kube.rs/controllers/intro/). Skim it now and
  come back to each chapter as the matching step comes up.

**Done when** you can explain the difference between `spec` and `status`, and why
controllers are *level-triggered* (they act on current state) rather than *edge-triggered* (they don't act on individual
change events).

### 1. Local cluster and dependencies

> **Safety first:** `kube::Client::try_default()` uses your kubeconfig's *current context*,
> just like `kubectl`. If that's a real cluster, your experiments will run there. Do all
> of this against a throwaway local cluster and check `kubectl config current-context`
> before running anything that writes.

**Build**

1. Install [kind](https://kind.sigs.k8s.io/) (it runs Kubernetes inside Docker) and
   create a cluster:
   ```sh
   kind create cluster --name learn      # switches your context to kind-learn
   kubectl get nodes
   ```
2. Add the dependencies:
   ```sh
   cargo add kube --features runtime,derive
   cargo add k8s-openapi --features latest
   cargo add tokio --features macros,rt-multi-thread,time
   cargo add serde --features derive
   cargo add tracing-subscriber --features env-filter
   cargo add futures anyhow thiserror serde_json schemars tracing
   ```
   Later steps add a few more (a web server, metrics, test helpers) when they are needed.

**Notes**

- `kube` and `k8s-openapi` are released as a pair. Always upgrade them together, and read
  [kube.rs: upgrading](https://kube.rs/upgrading/) before you do.
- `k8s-openapi` needs exactly one Kubernetes-version feature, set by the final binary.
  `latest` is the recommended default, even against older clusters. Pin a specific
  `v1_NN` only if you program against alpha or deprecated APIs. See
  [kube.rs: Kubernetes version](https://kube.rs/kubernetes-version/).
- Your `schemars` major version must match the one `kube` uses (1.x for kube 2 and
  later). If `cargo tree -i schemars` shows two versions, align yours.
- kube uses rustls by default, so nothing here needs OpenSSL.
- `tokio`'s `full` feature works too, but listing the features you use keeps builds
  smaller and makes the dependency honest.
- There is no YAML crate in the list on purpose. `serde_yaml` is deprecated, and
  `kubectl` accepts JSON everywhere. If you want YAML output later, kube itself uses
  `serde-saphyr`.

**Done when** `cargo build` succeeds and `kubectl get nodes` shows the kind node.

## Phase 1: Talking to the API server

### 2. Connect to the cluster: `examples/02_connect.rs`

**Learn**

- `Client::try_default()`: tries your kubeconfig, then falls back to in-cluster config.
- `kube::Config::infer()` and `kube::config::Kubeconfig` for more control.
- `#[tokio::main]` and returning `anyhow::Result<()>` from `main`.
- Setting up `tracing_subscriber` with `RUST_LOG` (try `RUST_LOG=info,kube=debug`).

**Build**

- Print the API server's version (`client.apiserver_version()`).
- Write a guard that reads the kubeconfig (`Kubeconfig::read()`) and refuses to run unless
  the current context starts with `kind-`. Put it in `src/lib.rs` so every later example
  and integration test can call it, rather than copying it around. The operator binary
  itself must not call it, because it has no kubeconfig when it runs in a cluster.

**Done when** the example prints the kind cluster's version, and the guard refuses to
run after you temporarily switch contexts.

### 3. Read typed resources: `examples/03_list_pods.rs`

**Learn**

- `Api<K>` constructors: `Api::namespaced`, `Api::all`, `Api::default_namespaced`.
- `list` with `ListParams` (label and field selectors, `limit` for paging), `get`, and
  `get_opt` for "it may not exist".
- `k8s-openapi` types. Nearly every field is an `Option`, so get comfortable unwrapping
  them cleanly. This is where let-chains and `as_deref()` earn their keep.
- `ResourceExt` helpers: `name_any()`, `namespace()`, `labels()`.

**Build** List pods in all namespaces and print namespace, name, phase, and node. Then
add an optional `--selector` argument.

**Done when** your output shows the same pods as `kubectl get pods -A -o wide`, and the
code contains no `unwrap()`.

### 4. Write resources with server-side apply: `examples/04_configmap_apply.rs`

**Learn**

- `create` with `PostParams`, `delete` with `DeleteParams`, `replace`.
- `replace` is read-modify-write: it fails with a 409 Conflict when the object's
  `resourceVersion` has moved on. That is optimistic concurrency, and it is why
  controllers avoid it.
- `patch` with `Patch::Merge`, `Patch::Json`, and `Patch::Apply`.
- **Server-side apply (SSA)**: `PatchParams::apply("learn-kube")` plus `Patch::Apply`.
  It's the standard way controllers write objects. You send the full desired state every
  time, the call is idempotent, and the API server tracks which *field manager* owns each
  field. A field you applied before and leave out now is removed, so an apply is a
  complete statement of intent, not a diff.
- Reading API errors: match `kube::Error::Api(status)` and use the helpers on `Status`
  (`is_not_found()`, `is_conflict()`, `is_already_exists()`) instead of comparing codes.
- [Server-Side Apply docs](https://kubernetes.io/docs/reference/using-api/server-side-apply/)

**Build**

1. Apply a ConfigMap with SSA. Run the example twice; the second run should change
   nothing.
2. Change a value and run it again. Inspect the result with
   `kubectl get cm <name> -o yaml --show-managed-fields`.
3. Change the same field with `kubectl edit`, then run the example again. You'll get a
   conflict. Add `.force()` and run it once more.
4. Apply again with one key left out and watch it disappear.
5. Delete the ConfigMap with `DeleteParams`. Make a second delete succeed quietly by
   treating "not found" as success.

**Done when** you can explain what `.force()` does and why controllers usually set it,
and why a key you stop applying gets removed.

### 5. Dynamic API and discovery (optional): `examples/05_dynamic.rs`

**Learn** `DynamicObject`, `ApiResource`, `GroupVersionKind`, and `kube::Discovery`
(prefer `run_aggregated()`, which needs far fewer round trips). Build the `Api` with
`Api::dynamic(client, &api_resource, &capabilities.scope)`, which picks the right URL for
namespaced and cluster-scoped kinds. These are for working with types you don't know at
compile time.

**Build** A mini `kubectl get`: take a resource name (for example `deployments`) as an
argument, resolve it with discovery, and list the objects.

**Done when** it works for `deployments`, `nodes`, and (after step 8) `webpages`.

## Phase 2: Watching for changes

### 6. Watchers: `examples/06_watch_pods.rs`

**Learn**

- `kube::runtime::watcher(api, watcher::Config::default())` and the `watcher::Event`
  variants: `Apply` and `Delete` for changes, and `Init` / `InitApply` / `InitDone` for the (re)list that happens at
  startup and after a desync.
- `watcher::Config` narrows what you watch: `.labels(...)`, `.fields(...)`.
- `WatchStreamExt`: `.default_backoff()`, `.applied_objects()`, `.touched_objects()`.
  Always add a backoff. Without one, a failing watch retries in a tight loop.
- Streams are lazy and must be pinned to be iterated: `std::pin::pin!` plus
  `try_next().await`.
- Watch events are not a reliable change log. You can miss intermediate states, and the
  watcher re-lists after a disconnect. This is why controllers are level-triggered.
- [kube.rs: streams](https://kube.rs/controllers/streams/)

**Build** Print pod creates, updates, and deletes while you run `kubectl run` and
`kubectl delete pod` in another terminal. Then restart the control plane with
`docker restart learn-control-plane` and watch the stream recover.

**Done when** the stream survives the control-plane restart without crashing, and you can
say which events you would have missed if the restart had taken longer.

### 7. Reflectors and stores: `examples/07_reflector.rs`

**Learn**

- `reflector::store()` returns a reader and writer pair. `reflector(writer, stream)`
  keeps the store updated.
- `Store::state()`, `Store::get()`, `wait_until_ready()`. The store hands out
  `Arc<K>`, so reads are cheap.
- The store only updates while its stream is being polled. Drive the stream in a spawned
  task or a `tokio::select!` branch; if nothing polls it, the cache silently goes stale.
- Caches let controllers read cluster state without calling the API server on every
  read. A cache read can be slightly behind the API server, and reconcilers have to
  tolerate that.
- Metadata-only watches: use `Api::<PartialObjectMeta<Pod>>` with the normal `watcher`.
  It uses much less memory and bandwidth when you only need names, labels, and owner
  references. (This replaces the deprecated `metadata_watcher` function.)

**Build** Keep a cache of all pods. Every 5 seconds, print pod counts by phase, read from
the cache rather than the API.

**Done when** the counts update as pods change, and `RUST_LOG=kube=debug` shows no new
list calls after startup.

## Phase 3: Custom resources

### 8. Define a custom resource: `src/lib.rs` + `examples/crdgen.rs`

**Learn**

- `#[derive(CustomResource)]` generates the `Webpage` type from `WebpageSpec`.
- `#[kube(...)]` attributes: `group`, `version`, `kind`, `namespaced`, `status`,
  `shortname`, `category`, `printcolumn(...)`, `doc`.
- `CustomResourceExt::crd()` builds the CRD manifest. `schemars` generates the
  OpenAPI schema from your Rust types, and doc comments become field descriptions.
- Why Kubernetes requires *structural* schemas, and what the API server does with one:
  it prunes unknown fields, applies defaults, and validates.
- Optional fields and defaults: `Option<T>`, `#[serde(default)]`, and
  `#[serde(default = "path")]`. A serde default also lands in the schema, so the API
  server fills it in for clients that omit the field.
- **Validation, cheapest first:**
    1. Schema keywords through schemars attributes, for example
       `#[schemars(range(min = 0, max = 10))]` and `#[schemars(length(max = ...))]`.
    2. [CEL rules](https://kubernetes.io/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/#validation-rules)
       for anything a keyword can't say (cross-field rules, immutability with `oldSelf`).
       Derive `KubeSchema` instead of `JsonSchema`, then use
       `#[x_kube(validation = ...)]` on fields and `#[kube(validation = ...)]` on the whole
       resource. The API server enforces these with no webhook to run.
    3. Checks at reconcile time, reported as a condition (step 12).
- API design: read the `spec`/`status` sections of the
  [Kubernetes API conventions](https://github.com/kubernetes/community/blob/master/contributors/devel/sig-architecture/api-conventions.md).
  Start at `v1alpha1`. Once others depend on a version, only make compatible changes (add optional fields; never rename,
  remove, or tighten).
- [kube.rs: schemas](https://kube.rs/controllers/schemas/) and
  [admission](https://kube.rs/controllers/admission/)

**Build** Start with something like this (change the group to a domain you control):

```rust
use kube::CustomResource;
use schemars::JsonSchema;
use serde::{Deserialize, Serialize};

/// A static web page served by nginx.
#[derive(CustomResource, Deserialize, Serialize, Clone, Debug, JsonSchema)]
#[kube(group = "demo.example.com", version = "v1alpha1", kind = "Webpage", namespaced)]
#[kube(status = "WebpageStatus", shortname = "wp")]
#[serde(rename_all = "camelCase")]
pub struct WebpageSpec {
    /// The HTML document to serve as `index.html`.
    pub html: String,
    /// How many nginx pods to run.
    pub replicas: i32,
}

/// Observed state of a `Webpage`, written only by the operator.
#[derive(Deserialize, Serialize, Clone, Debug, Default, JsonSchema)]
#[serde(rename_all = "camelCase")]
pub struct WebpageStatus {
    /// Ready pods, as reported by the Deployment.
    pub ready_replicas: i32,
    /// The `metadata.generation` this status was computed from.
    pub observed_generation: Option<i64>,
}
```

1. Write `examples/crdgen.rs` to print the CRD as JSON, then install it with
   `cargo run --example crdgen | kubectl apply -f -`.
2. Write a sample `Webpage` manifest and apply it. Check `kubectl get wp`.
3. Give `replicas` a default of 1 and a range of 0 to 10. Cap the length of `html` well
   below the 1 MiB ConfigMap limit. Regenerate and re-apply the CRD.
4. Switch the spec to `KubeSchema` and add one CEL rule with a custom message. For
   example, require a full HTML document:
   `self.lowerAscii().startsWith('<!doctype html>')`.
5. Save the generated CRD as `manifests/crd.json` and commit it. Add a unit test that
   fails when the file no longer matches `Webpage::crd()`, so schema changes always show
   up in review.

**Done when**

- `kubectl explain webpage.spec` shows your fields with their descriptions.
- A `Webpage` without `replicas` comes back with `replicas: 1`.
- The API server rejects `replicas: 50`, and rejects HTML that breaks your CEL rule with
  your message.
- The drift test fails when you change the spec struct without regenerating.

## Phase 4: Building the operator

### 9. First controller: `src/main.rs`

**Learn**

- `Controller::new(Api<Webpage>, watcher::Config::default())`
- `.run(reconcile, error_policy, Arc<Context>)`, `.shutdown_on_signal()`, and consuming
  the stream with `.for_each(...)`. The controller does nothing unless that stream is
  polled. Log the errors it yields.
- The reconcile signature:
  `async fn reconcile(obj: Arc<Webpage>, ctx: Arc<Context>) -> Result<Action, Error>`
- `Action::requeue(Duration)` vs `Action::await_change()`. A periodic requeue is a
  safety net for missed events, not the main trigger.
- The reconciler receives the *object*, not the *event*. It has to work out what to do
  from current state alone. The object comes from the controller's cache, so it may be a
  moment out of date.
- What the runtime guarantees: one reconcile at a time per object, different objects
  concurrently, and repeated triggers for a busy object collapsed into one.
- [kube.rs: the reconciler](https://kube.rs/controllers/reconciler/) (read the section on
  idempotency twice) and [the application](https://kube.rs/controllers/application/).

**Build**

- A controller whose reconcile function only logs the `Webpage` it received and returns
  `Action::requeue` after 5 minutes. Put a `kube::Client` in `Context`.
- At startup, check that the CRD is installed (a `list` with `limit(1)` is enough) and
  exit with a clear message if it isn't.

**Done when** creating and editing a `Webpage` triggers reconciles, Ctrl-C shuts the
controller down cleanly, and you can explain why deleting a `Webpage` *doesn't* reconcile
it. The object is gone, which is why step 13 exists.

### 10. Manage child resources

**Learn**

- Write desired state as pure functions, for example
  `fn desired_deployment(wp: &Webpage) -> Deployment`. No client, no `async`, so they are
  trivial to test.
- Owner references: `wp.controller_owner_ref(&())`. Kubernetes garbage-collects the
  children when the owner is deleted. It returns an `Option`; work out when it is `None`
  and turn that into an error instead of unwrapping.
- Apply each child with SSA (step 4), using one constant field-manager name and
  `.force()`. Typed `k8s-openapi` objects serialize `apiVersion` and `kind` for you.
- Set only the fields you own. Anything you put in the applied object, you will fight
  other writers over on every reconcile.
- Naming and labels: derive child names from the `Webpage` name so they are
  deterministic, and use the
  [recommended labels](https://kubernetes.io/docs/concepts/overview/working-with-objects/common-labels/)
  (`app.kubernetes.io/name`, `/instance`, `/managed-by`). A Deployment's `spec.selector`
  is immutable, so choose selector labels you will never need to change.
- `.owns(Api::<Deployment>::all(client), watcher::Config::default())` so that changes
  to children trigger a reconcile of their owner.
- [kube.rs: related objects](https://kube.rs/controllers/relations/) and
  [garbage collection](https://kube.rs/controllers/gc/)

**Build** For each `Webpage`, apply:

- a ConfigMap whose `index.html` key holds `spec.html`
- a Deployment running `nginx` with that ConfigMap mounted at `/usr/share/nginx/html`,
  and `spec.replicas` replicas
- a Service in front of the Deployment

Write unit tests for the three builder functions as you go: the owner reference is set,
replicas follow the spec, and the Service selector matches the pod template labels.

**Done when**

- `kubectl port-forward svc/<name> 8080:80` serves your HTML.
- Deleting the Deployment by hand causes it to come back.
- Scaling the Deployment by hand gets reverted.
- Deleting the `Webpage` garbage-collects all three children.
- `cargo test` passes without a cluster.
- You've noticed how long an edit to `spec.html` takes to appear (ConfigMap volume
  propagation delay). Optional: put a hash of the HTML in a pod-template annotation so
  that content changes roll the pods immediately.

### 11. Status and conditions

**Learn**

- The status subresource and `Api::patch_status`. Status is *observed* state: compute it
  from the children, never copy it from the spec.
- Use SSA for status too. A status apply needs `apiVersion` and `kind` in the body next to
  `status`. (`Patch::Merge` with `{"status": ...}` also works and is fine while learning.)
- `observedGeneration`: tells a reader whether the status reflects the spec they just
  wrote.
- Conditions (`k8s_openapi::apimachinery::pkg::apis::meta::v1::Condition`) and the
  [API conventions](https://github.com/kubernetes/community/blob/master/contributors/devel/sig-architecture/api-conventions.md#typical-status-properties)
  for them: a `type` such as `Ready`, `status` of `True`/`False`/`Unknown`, a CamelCase
  `reason`, a human `message`, and a `lastTransitionTime` that changes only when `status`
  flips. Timestamps are `jiff` values now, not `chrono`.
- The schema for a list of conditions should be a map keyed by `type`
  (`x-kubernetes-list-type: map`), so appliers merge entries instead of replacing the
  list. kube's [`crd_derive` example](https://github.com/kube-rs/kube/blob/main/examples/crd_derive.rs)
  shows how.
- `#[kube(printcolumn(...))]` for `kubectl get` output.
- **Hot loops.** Writing status creates a watch event, which triggers another reconcile.
  The main defence is a *deterministic* status: if nothing changed, the patch is a no-op
  and the loop stops after one extra pass. Putting "now" in status on every reconcile
  spins forever.
- The second defence is filtering: `predicate_filter(predicates::generation, ...)` drops
  status-only events. You don't need it here. It requires the `unstable-runtime` feature (`Controller::for_stream`), and
  a generation-only filter can hide the events that
  finalizers and deleted children depend on. Read the `predicates` module docs before
  ever using it.
- [kube.rs: optimization, "repeatedly triggering yourself"](https://kube.rs/controllers/optimization/#repeatedly-triggering-yourself)

**Build** Set `readyReplicas` from the Deployment's status, set `observedGeneration`, and
add a `Ready` condition. Add a `READY` print column.

**Done when** `kubectl get wp` shows readiness,
`kubectl wait --for=condition=Ready wp/<name>` returns, and reconcile logs go quiet once
the cluster is idle (no hot loop).

### 12. Errors, retries, and Events

**Learn**

- A `thiserror` error enum for the controller. Wrap `kube::Error` with `#[from]` or
  `#[source]`, and give each failure its own variant so logs and metrics can tell them
  apart.
- Sort failures into two kinds:
    - **Transient** (API timeouts, conflicts, a child not ready yet): return `Err`.
      `error_policy(obj, &err, ctx) -> Action` then decides when to try again.
    - **Permanent until the user acts** (a spec the operator can't satisfy): don't return
      `Err`. Set `Ready=False` with a reason, emit a Warning Event, and return
      `Action::await_change()`. Retrying can't fix it; a spec change will trigger a new
      reconcile anyway.
- kube has no built-in per-object exponential backoff. A fixed requeue delay in
  `error_policy` is the common choice. Below that, the client already retries throttled
  and unavailable responses (429, 503, 504) with its own backoff.
- Kubernetes Events with `kube::runtime::events::Recorder` (it writes
  `events.k8s.io/v1` Events). They show up in `kubectl describe`. Events are for humans:
  emit them on transitions, not on every reconcile, and never read them back as state.
- `tracing` spans per reconcile (`#[instrument(skip(ctx), fields(...))]`) that include
  the object's name and namespace.

**Build** The length cap from step 8 counts characters, not bytes, so HTML full of
multi-byte characters can pass the schema and still exceed the 1 MiB ConfigMap limit.
Check the byte size in reconcile. For an oversized `Webpage`, set `Ready=False` with
reason `HtmlTooLarge`, emit a `Warning` Event once, and wait for a change instead of
retrying.

**Done when** `kubectl describe wp <name>` shows your Event and condition, the oversized
`Webpage` is not being retried, and it neither crashes the controller nor blocks other
`Webpage`s from reconciling. Fixing the HTML makes it `Ready` with no restart.

### 13. Finalizers

**Learn**

- When you need a finalizer: to clean up anything owner references can't, such as
  external systems, cluster-scoped objects, or objects in another namespace.
- `kube::runtime::finalizer::finalizer(&api, NAME, obj, |event| async { ... })`, matching
  on `finalizer::Event::Apply` and `finalizer::Event::Cleanup`. Make it the only
  top-level action in `reconcile`. Its error type wraps yours, which is one reason the
  controller needs a real error enum rather than `anyhow`.
- The rules: both branches must be idempotent. `Cleanup` must work even if `Apply` never
  ran, and must treat "already gone" as success. Use a domain-qualified finalizer name
  such as `demo.example.com/index`.
- The cost: while the controller is down or `Cleanup` keeps failing, deletes hang.
- [kube.rs: garbage collection](https://kube.rs/controllers/gc/)

**Build** Keep a cluster-wide "index" ConfigMap in a fixed namespace with one key per
`Webpage`. A `/` isn't allowed in ConfigMap keys, so use `<namespace>.<name>`. Owner
references can't cross namespaces, so use a finalizer to remove each entry when its
`Webpage` is deleted.

Reconciles for different `Webpage`s run concurrently and all write the same ConfigMap.
Before you write the code, work out why applying a single key with a shared SSA field
manager would delete everyone else's entries, and pick a patch type that is safe here.

**Done when** deleting a `Webpage` removes its index entry, and creating twenty at once
leaves twenty entries. You can also explain what happens when the controller is down
while someone deletes a `Webpage` (it stays in `Terminating`), and how to remove the
finalizer by hand in an emergency.

### 14. Watching related resources

**Learn**

- `.watches(api, config, mapper)` maps changes in *non-owned* objects to the objects
  that should be reconciled.
- `ObjectRef`, and using the controller's own cache (`Controller::store()`) inside the
  mapper to find which `Webpage`s refer to the object that changed.
- A reference to something that doesn't exist yet is a normal state, not an error to
  retry in a loop. Report it as a condition and let the watch wake you up.

**Build** Add an optional `spec.htmlFrom.configMapName`, so that a `Webpage` can take its
HTML from a ConfigMap the user manages. `html` becomes optional. Add a CEL rule on the
spec so that exactly one of the two is set: `has(self.html) != has(self.htmlFrom)`.

**Done when**

- Editing the user's ConfigMap updates the served page without touching the `Webpage`.
- A `Webpage` that names a missing ConfigMap shows `Ready=False` with a clear reason, and
  becomes `Ready` on its own when the ConfigMap is created.
- The API server rejects a `Webpage` with both fields, or neither.

## Phase 5: Production readiness

### 15. Testing the reconciler

You already have unit tests for the builders (step 10) and the CRD drift test (step 8).
This step covers the code that talks to Kubernetes.

**Learn**

- The four layers in [kube.rs: testing](https://kube.rs/controllers/testing/): plain
  unit tests, unit tests with a mocked API server, integration tests against a real
  cluster, and end-to-end tests with the operator running in the cluster. Cost and
  flakiness rise as you go up, so keep most tests at the bottom.
- Mocking the API server with `tower-test`: build a `Client` from a mock service (`Client::new`) and assert on the
  requests the reconciler sends. See `fixtures.rs` in
  [kube-rs/controller-rs](https://github.com/kube-rs/controller-rs).
- The [`envtest`](https://crates.io/crates/envtest) crate runs a real API server and etcd
  with no nodes. It is a middle ground when mocks get unwieldy.
- Integration tests against kind in `tests/`, marked `#[ignore]` and run with
  `cargo test -- --ignored`. Call the kind-context guard from step 2 first. Give each
  test its own namespace and wrap every wait in `tokio::time::timeout`.
- `kube::runtime::wait::await_condition` and the ready-made checks in
  `wait::conditions` for waiting on state in tests.

**Build**

- One mocked test for a reconcile path, for example "a new `Webpage` gets the finalizer
  added".
- One integration test that creates a `Webpage`, waits for it to become `Ready`, deletes
  it, and waits for it to be gone.

**Done when** `cargo test` passes with no cluster, and
`cargo test -- --ignored` passes against kind.

### 16. Observability

**Learn**

- Logs: JSON output in the cluster (`tracing-subscriber`'s `json` feature) and
  human-readable locally, chosen by an environment variable or flag.
- Metrics with `prometheus-client`. Three cover most needs: a reconcile counter, a
  failure counter labelled by error variant, and a reconcile duration histogram.
- A small web server next to the controller for `/metrics` and a health endpoint. `axum`
  is the usual choice; controller-rs uses `actix-web`. Run the server and the controller
  together (`tokio::join!`) and stop both on the same shutdown signal.
- Optional: OpenTelemetry traces with `tracing-opentelemetry`, so each reconcile is a
  trace you can follow.
- [kube.rs: observability](https://kube.rs/controllers/observability/)

**Build** Serve `/metrics` and `/healthz` on one port. Record the three metrics from
`reconcile` and `error_policy`.

**Done when** `curl localhost:8080/metrics` shows the reconcile rate and error count
moving while you create, break, and delete `Webpage`s.

### 17. Package and deploy

**Learn**

- A multi-stage Dockerfile. Cache dependency builds (`cargo-chef` or BuildKit cache
  mounts), and use a minimal runtime image that runs as non-root, such as distroless or
  Chainguard `static` with a musl build. Avoid `scratch`, which defaults to root.
- `kind load docker-image` to get local images into the cluster.
- RBAC with least privilege: a ServiceAccount plus a ClusterRole granting only what the
  controller uses.
    - `webpages`: get, list, watch, patch (patch is for the finalizer)
    - `webpages/status`: patch
    - `webpages/finalizers`: update (only checked on clusters that enforce owner-reference
      permissions, such as OpenShift, but harmless elsewhere)
    - `configmaps`, `services`, `deployments`: get, list, watch, create, patch
    - `events` in the `events.k8s.io` group: create, patch

  SSA needs `create` as well as `patch`. Nothing needs `delete`, because garbage
  collection removes the children. The CRD is installed separately, so the operator needs
  no access to `customresourcedefinitions`.
- Pod hardening: `runAsNonRoot`, `allowPrivilegeEscalation: false`,
  `readOnlyRootFilesystem: true`, `capabilities.drop: ["ALL"]`, resource requests and
  limits, and the operator in its own namespace.
- Liveness and readiness probes on the health endpoint from step 16, and graceful
  shutdown: `shutdown_on_signal()` lets running reconciles finish before the pod exits.
- Run **one replica**. Two replicas of a plain controller both reconcile everything.
  Use the `Recreate` deployment strategy so a rollout never runs old and new side by side.
- [kube.rs: security](https://kube.rs/controllers/security/) and
  [manifests](https://kube.rs/controllers/manifests/)

**Build** A Dockerfile, and manifests in `manifests/` for the namespace, RBAC, and the
operator Deployment. Check your RBAC with
`kubectl auth can-i --list --as=system:serviceaccount:<ns>:<sa>`.

**Done when** the operator runs as a Deployment in kind, every check from steps 10 to 14
still passes with no local process running, and removing one verb from the ClusterRole
produces a clear error in the operator's logs.

### 18. Tune and scale

**Learn**

- Reconcile concurrency is **unbounded** by default. Cap it with
  `controller::Config::default().concurrency(n)` via `.with_config(...)`. `debounce`
  on the same config merges bursts of events at the cost of a slower response.
- Watch less. Scope an `Api` to a namespace when you can, and give watchers selectors:
  a label selector on the `.owns(...)` watches means the operator only lists and caches
  the children it manages, not every Deployment in the cluster.
- Smaller initial lists: `watcher::Config::page_size`, or `.streaming_lists()` on
  clusters that support it.
- Metadata-only watches for children (`PartialObjectMeta`, step 7) where the reconciler
  only needs to know that something changed.
- High availability: a controller tolerates short downtime well, so a single replica is
  the recommended default. kube has no built-in leader election. If you need a standby,
  use a third-party crate (`kube-lease-manager`, `kube-leader-election`, or
  `kubert::lease`) and grant access to `leases` in `coordination.k8s.io`.
- [kube.rs: optimization](https://kube.rs/controllers/optimization/),
  [scaling](https://kube.rs/controllers/scaling/), and
  [availability](https://kube.rs/controllers/availability/)

**Build** Set a concurrency limit and add a label selector to the owned watches. Then
create a couple of hundred `Webpage`s in a loop and watch your metrics from step 16.

**Done when** in-flight reconciles never exceed your limit during the burst, the debug
logs show the label selector on the child list and watch requests, and every `Webpage`
ends up `Ready`.

### 19. CI and supply chain

**Learn**

- What CI already enforces here: `cargo fmt --check`, `cargo clippy -D warnings`, and
  `cargo test`.
- Dependency checks: [`cargo deny`](https://embarkstudios.github.io/cargo-deny/) for
  security advisories, licences, and duplicate or banned crates.
- Automated updates with Dependabot or Renovate, with `kube` and `k8s-openapi` grouped so
  they always move together ([kube.rs: upgrading](https://kube.rs/upgrading/) has the
  config).
- Running the integration tests in CI against a kind cluster.
- Pinning third-party GitHub Actions to a commit SHA.

**Build** Add a `deny.toml` and a `cargo deny check` job. Add an update config that
groups the kube crates. Add a CI job that creates a kind cluster, installs the CRD, and
runs `cargo test -- --ignored`.

**Done when** a pull request runs lint, unit tests, integration tests, and dependency
checks, and all of them pass.

## Stretch goals

- **Scale subresource:** add `#[kube(scale(...))]` so `kubectl scale wp` and a
  HorizontalPodAutoscaler can drive `spec.replicas`.
- **CRD versioning:** add `v1beta1`, combine the versions with `merge_crds`, then write a
  conversion webhook between them.
- **Client-side CEL:** enable kube's `cel` feature and `#[kube(cel)]`, then unit-test your
  validation rules with `validate_cel()` without a cluster.
- **Admission webhook:** a validating or mutating webhook using `kube::core::admission`,
  for a rule CEL can't express. Compare it with a `ValidatingAdmissionPolicy`.
- **Leader election:** run two replicas with one of the crates from step 18 and kill the
  leader mid-reconcile.
- **Workspace split:** move the CRD types into their own crate (for example
  `crates/webpage-crd`) so other tools can use them without pulling in the operator.
- **Multiple controllers:** run two controllers in one process that share reflectors (`unstable-runtime`).
- **Packaging:** turn `manifests/` into a Helm chart or a kustomize base.
- **Compare your code:** read [controller-rs](https://github.com/kube-rs/controller-rs)
  from start to finish and compare it with your operator.
